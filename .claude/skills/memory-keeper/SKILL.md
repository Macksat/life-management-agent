# Memory Keeper

## 目的

会話を通じて得られたユーザーの**プロフィール情報**（好み・判断基準・個人的事実）を
`data/llm_wiki/sources/memories/` に蓄積し、**セッションをまたいだ長期記憶**を実現する。

- `user_context.md` = 「この人は何者か」（役割・スタック・関心）
- `memories/` = 「この人はどんな人か」（属性・好み・判断基準・行動パターン）

> **重要: `data/llm_wiki/sources/memories/` はプロフィール情報専用。**
> 会話の内容や思考の過程そのものは `data/llm_wiki/sources/second_brain/` に保存する（AGENTS.md §17）。

## 保存先

```
data/llm_wiki/sources/memories/
├── preferences.md   # 好み・スタイル・行動パターン
├── decisions.md     # 重要な意思決定と根拠
└── facts.md         # 個人に関する事実情報
```

## 記憶の種類と保存先マッピング

| ファイル | 記録するもの | 例 |
|---|---|---|
| **preferences.md** | 好み・スタイル・パターン | 「箇条書き派」「承認は最小限」「FastAPI 好き」 |
| **decisions.md** | 判断とその根拠・背景 | 「LangGraph を採用 → 理由: 状態管理が明示的」 |
| **facts.md** | 個人に関する客観的事実 | 「〇〇市在住」「猫を飼っている」「毎朝ランニングする」 |

### preferences.md のカテゴリ

| セクション | 内容 |
|---|---|
| 対話スタイル | 出力形式、言語、詳細度の好み |
| 作業パターン | 時間帯、進め方、習慣 |
| 技術的な好み | 言語・FW・ツールの選好 |
| 意思決定スタイル | 選択肢の出し方、判断の仕方 |
| ツール・ワークフロー | Issue 運用、コミット、開発環境の好み |

### decisions.md のカテゴリ

| セクション | 内容 |
|---|---|
| 技術・設計 | 技術選定、アーキテクチャ判断 |
| 生活・行動 | 日常生活に関する決定 |
| 方針・戦略 | このリポジトリや行動 OS の運用方針 |

### facts.md のカテゴリ

| セクション | 内容 |
|---|---|
| 基本情報 | 居住地域（市区町村レベル）、職業など |
| 趣味・関心 | 趣味、好きなもの、習い事 |
| 生活環境 | 利用サービス、生活圏、通勤手段など |

> **注意:** facts.md は AGENTS.md §8（機微情報ルール）を厳守。
> パスワード・API キー・口座番号・カード番号・詳細住所・電話番号等の高リスク情報は**記録しない**。
> 一方で、このリポジトリはローカル参照前提のため、人間関係・仕事・生活の整理に有用なら、人物を特定できる名前・呼称・関係性は保持してよい。

## いつ発動するか

### 書き込み（自動・承認不要）

以下のタイミングで **承認なしに** 書き込む:

1. **会話中に好み・パターン・事実を観察したとき**（プロアクティブ）
2. ユーザーが「覚えておいて」「メモして」「remember this」と言ったとき
3. ユーザーが重要な意思決定をしたとき（判断 + 根拠をセットで記録）
4. ユーザーが**人物の役割対応や関係性の誤読を訂正したとき**（例: 「この人は友人」「この人はパートナー」「この場の参加者は3人」）

### 読み込み（参照タイミング）

読み込みは「必要なら読む」ではなく、**以下の条件では必ず読む**。ただし参照はまず LLMWiki を使い、source-of-truth の更新や精読が必要なときだけ `data/llm_wiki/sources/memories/` を直接読む。

| タイミング | 読むファイル | トリガー |
|---|---|---|
| **セッション開始時** | 全ファイル | CLAUDE.md 読み込み順 #3 |
| **ユーザー個人に関する情報を扱うとき** | `facts.md` を必須。必要に応じて `preferences.md` / `decisions.md` | 生活・健康・習慣・居住地・所有物・日常行動・個人向け提案 |
| **設計・技術判断時** | `decisions.md` + `preferences.md` | 技術選定、アーキテクチャの議論 |
| **Issue 作成・提案時** | `preferences.md`。個人に紐づく内容なら `facts.md` も読む | interactive-intake 実行時 |
| **行動提案・助言時** | `preferences.md` + `decisions.md`。個人文脈が絡むなら `facts.md` も読む | 進め方の提案、優先度の相談、選択肢提示 |
| **「何を覚えてる？」と記憶照会されたとき** | `facts.md` / `preferences.md` / `decisions.md` に加え、必要な GitHub Issue を読む | 目標、継続タスク、方針、ライフゴール、進行中の記録の確認 |
| **定期棚卸し時** | 全ファイル | 記憶の整理・統合 |

**原則: ユーザー個人に関する情報を扱う場面では、まず LLMWiki の `people_self` を起点に読み、必要な範囲で正本の `facts.md` `preferences.md` `decisions.md` を追加で読む。**

**記憶照会の追加原則:** ユーザーが「覚えてる？」「目標覚えてる？」「前に決めたこと覚えてる？」のように、**記憶そのものの有無や内容**を聞いたときは、`data/llm_wiki/sources/memories/` だけで完結させず、必要に応じて GitHub Issue も確認する。特に、ライフゴール、継続中の project、日次・週次で管理している事項は、Issue 側が正本の可能性が高い。

### 参照の最小単位

- 全ファイルを毎回読むのではなく、**該当するファイルだけ**読む
- 個人情報の確認だけなら `facts.md`
- 表現や提案の出し方まで合わせるなら `preferences.md` を追加
- 過去判断との整合が必要なら `decisions.md` を追加
- 目標、継続タスク、進行中の方針、ライフゴールの確認なら **関連する GitHub Issue も追加で読む**
- 読んだ結果、関連エントリが無ければ無理に補わない

### 記憶照会時の GitHub Issue 参照ルール

- GitHub Issue の参照は、速度優先で `gh` CLI / ローカルキャッシュ / GitHub MCP のいずれを使ってもよい。
- `data/llm_wiki/sources/memories/` に十分な情報がない場合だけでなく、**Issue 側が正本になりやすい話題**では最初から Issue を見る。
- 例:
  - ライフゴール・人生目標 → `#12 ライフゴール ダッシュボード` とサブ Issue
  - 継続中のプロジェクトや方針 → 関連する open Issue
  - 最近決めたことが会話メモより Issue にまとまっていそうな場合 → タイトルやキーワードで検索した Issue
- 回答では、「memory files にある内容」と「Issue にある内容」を混同せず、必要なら「Issue 側ではこうなっている」と分けて述べる。
- GitHub MCP が使えない場合は、その時点で「Issue 側は未確認」と明示し、memory files だけを根拠に答える。

## 書き込み手順

```
1. 会話中に記録すべき情報を観察する
2. 対象ファイル（preferences / decisions / facts）を特定
3. まず LLMWiki で近い既存文脈を確認する
4. 該当ファイルを読む
5. 重複チェック: 既に記録済みなら書き込まない
6. 矛盾チェック: 既存と矛盾する場合は上書き更新し、変更履歴に記録
7. 肥大化チェック: ファイルがサイズ上限に近い場合、先に整理してから追記
8. 該当セクションに追記 or 更新
9. 変更履歴に 1 行追加（日付 + 変更内容）
10. 「最終更新」日付を今日に更新
11. **Wiki を再ビルドする** — `python3 scripts/build_llm_wiki.py` を実行する
```

> **ルーティン除外の仕組み:** 挨拶・天気確認等のルーティン会話では memory-keeper が発動しない（記録すべき情報がない）ため、wiki rebuild も自然に発生しない。

**コミットはしない。** ユーザーが明示的に求めた場合のみコミットする。

## 書き込み判断基準

### 記録する

- ユーザーが明確に表明した好み・事実・判断
- 繰り返し現れるパターン（2回以上の観察が望ましい。明確な表明は1回でも可）
- 重要な意思決定とその根拠（「なぜそうしたか」をセットで）
- 作業効率に影響する習慣・パターン
- 今後の対話で活用できる個人的事実
- 継続的に効く運用ルール・例外条件（例: どこで確認を要するか）
- 会話ログや過去要約に出てくる**人物の役割対応**（誰がパートナー・友人・同僚か、どの集まりに誰がいたか）
- 呼称の揺れや誤読を防ぐための**関係ラベルの補正情報**（例: 「就職祝いの対象はパートナー本人」）

### 記録しない

- **会話の内容・思考の過程そのもの**（→ `data/llm_wiki/sources/second_brain/` に保存。AGENTS.md §17）
  - NG: 「転職について3つの選択肢を検討した」(会話の記録)
  - OK: 「意思決定の軸として長期的な納得感を最重視する」(プロフィール)
- 一度きりの偶発的な行動（「今回だけこうして」）
- 文脈依存の一時的な選択
- **機微情報**（AGENTS.md §8: パスワード、住所詳細、電話番号、口座番号など）
- 根拠のない推測（観察事実のみ記録する）
- 当たり前すぎること（改めて記録する価値がないもの）
- `user_context.md` に既に書かれていること（重複回避）
### 人間関係情報の扱い

- 人物の関係性が今後の対話に効くと判断したら、`facts.md` に短く残す
- 優先して残すのは、`パートナー / 友人 / 同僚 / 家族` の役割、参加した集まりの構成、呼称の補正情報
- ローカル運用上の有用性が高ければ、人物名・通称・関係ラベルをそのまま残してよい
- 既存の second_brain 要約に曖昧さがあっても、**まず memories 側で補正事実を追加**する。元の会話ダイジェストの全面修正は、ユーザーが明示的に求めたときだけ行う
- この種の補正を会話中に得たら、そのターン内で memory 更新と wiki rebuild まで行う

## 肥大化対策

記憶ファイルが際限なく膨らむことを防ぐための**ハードルール**。

### ファイルサイズ上限

| ファイル | コンテンツ行数上限 | セクション上限 |
|---|---|---|
| `preferences.md` | **80行**（見出し・空行除く実エントリ） | 各セクション 15 項目 |
| `decisions.md` | **60行** | 各セクション 12 項目 |
| `facts.md` | **40行** | 各セクション 10 項目 |

> 行数は目安。厳密にカウントする必要はないが、明らかに超えたら整理を優先する。

### 追記より更新を優先するルール

- 同じ意味のエントリがある場合、**新規追加ではなく既存行を更新**する
- 弱い観察を強い事実で置き換える（例: 「らしい」ではなく、本人明言に更新）
- 一時的な事情は恒久記憶にしない。継続しなかったものは追記せず削除候補にする
- 1 会話で 3 件以上の新規記憶を追加する場合、まず統合できないか確認する
- `変更履歴` は監査用の要点だけ残し、本文と重複する長い説明を書かない

### 整理のトリガーと手順

1. **書き込み前チェック:** ファイルが上限に近い場合、**新規追記の前に整理を行う**
2. **定期棚卸し時:** 全ファイルを通読し、以下を実施:
   - 古い記憶（3ヶ月以上前で最近参照されていないもの）を削除候補に
   - 類似エントリを統合（2→1 に要約）
   - 矛盾するエントリを新しい方に統一
   - `user_context.md` と重複する内容を削除
3. **decisions.md 固有:** 6ヶ月以上前で、もう参照価値のない判断は削除してよい
4. **ファイル欠落時:** `preferences.md` / `decisions.md` / `facts.md` のいずれかが無ければ、追記前にテンプレートを作成する

### 整理の優先順位

```
1. 重複を統合する（最優先）
2. user_context.md との重複を削除
3. 古い＋参照価値の低いエントリを削除
4. 類似エントリを要約統合
```

### 変更履歴の上限

- 各ファイルの変更履歴は **直近 20 件** まで。超えたら古いものから削除。

## フォーマット規約

### 共通ルール

- 各エントリは `- ` で始める
- 1 エントリ = 1〜2 行で簡潔に
- 観察日を末尾に `(YYYY-MM-DD 観察)` で付記
- 更新時は日付を `(YYYY-MM-DD 更新)` に変更

### decisions.md 固有

- 判断内容と根拠をセットで記録: `- [判断]: [根拠/背景] (YYYY-MM-DD)`
- 例: `- GitHub Issue ベースの個人 OS を採用: タスク管理アプリより自由度が高く、AI との連携が容易なため (2026-05-01)`

### facts.md 固有

- 客観的事実のみ。感情や評価は `preferences.md` へ
- 例: `- 〇〇市在住 (2026-06-01 観察)`

## 他スキル・セッションとの連携

### 3 レイヤの棲み分け（AGENTS.md §17）

| | `user_context.md` | `memories/`（本スキル） | `second_brain/` |
|---|---|---|---|
| **答える問い** | この人は何者か | この人はどんな人か | この人は何を考えてきたか |
| **内容** | 役割・スタック・関心・価値観 | 属性・好み・判断基準・パターン | 会話の内容・思考・洞察 |
| **粒度** | 大きな変化 | 1 行の箇条書き | 1 会話のダイジェスト |
| **更新頻度** | 週次 / 大きな変化時 | 随時（自動） | ユーザー指示時 |
| **管理スキル** | context-update | **memory-keeper** | llm-wiki-build |

**境界の判断:**
- 「この情報は、会話の文脈がなくても意味が通じるか？」 → **YES** なら `memories/`（プロフィール）
- 「この情報は、特定の会話・思考の流れの中でこそ意味があるか？」 → **YES** なら `second_brain/`（会話記録）
- 両方に該当 → second_brain に記録を残しつつ、プロフィール部分だけ memories/ に抽出

### 他スキルからの参照ガイド

| スキル | 参照すべき記憶 | 理由 |
|---|---|---|
| interactive-intake | `preferences.md` | Issue の書き方・形式の好みに合わせる |
| research-agent | `decisions.md` | 過去の判断と矛盾しない調査方向 |
| interactive-intake (`triage`) | `preferences.md` + `decisions.md` | 分類・優先度の判断に過去の方針を反映 |

個人情報を扱う他スキルは、該当処理の前に `facts.md` を読むこと。読み忘れた場合は、その場で読み直してから続行する。

### 定期棚卸しでの記憶整理

定期的な棚卸しの終盤に以下を実施:
1. `data/llm_wiki/sources/memories/` の全ファイルを読む
2. 肥大化チェック（上限超え → 整理）
3. 古い・矛盾する・重複するエントリを整理
4. `user_context.md` と重複する内容を削除
5. 変更履歴が 20 件超なら古いものを削除

## NG 例

- NG: 「たぶんこういう人だろう」と根拠なく推測を記録
- NG: 機微情報（詳細住所、電話番号、パスワード、口座番号）を記録
- NG: 1 回の会話の文脈だけで強い断定（「この人は絶対に〇〇派」）
- NG: サイズ上限を無視して追記し続ける
- NG: 既存の記憶を確認せず重複追記する
- NG: 会話のたびにコミットする（ユーザー指示時のみ）
- NG: decisions.md に根拠なしで判断だけ記録する
- NG: facts.md に主観的な評価を書く（→ preferences.md へ）
